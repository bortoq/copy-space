# In-Space Forth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Реализовать Forth целиком внутри адресного пространства так, чтобы после bootstrap он мог расширять сам себя собственными словами без парсинга, компиляции, хранения состояния или диспетчеризации на хосте.

**Architecture:** Реализация строится как внутреннее threaded-представление поверх `copy-space`: фиксированный boot-слой поддерживает `PROCESSOR`, исполняет `NEXT`, обслуживает два стека, словарь, heap и поток токенов. На первом контуре Forth работает не с текстом, а с внутренними токенами, числами и строковыми объектами в памяти; после этого внутри самого Forth добавляются именованный словарь, разбор чисел, строковые литералы и интерпретатор входного буфера.

**Tech Stack:** `doc/adress_space.md`, `doc/module_logic.md`, `doc/copy_optimization.md`, область `PROCESSOR`, область `REGISTER`, fixed layout в битовом пространстве, внутренние copy-инструкции, модуль загрузки следующего такта, без каналов, MMIO и runtime-хоста.

## Core Design Decisions

Ниже зафиксированы решения, которые снимают основные будущие блокеры. Во время реализации их не пересматривать, если только не обнаружено прямое противоречие определению пространства.

### 1. Форма первого Forth

Первый Forth не текстовый. Он работает с внутренним потоком токенов и literal cells.

Это устраняет стартовый блокер “как написать парсер до появления языка”.

### 2. Минимальная единица программы

Программа хранится как цепочка ячеек фиксированной ширины `CELL_BITS = ADDR_BITS`.

Каждая ячейка содержит одно из:

- execution token слова;
- literal number;
- адрес объекта данных;
- служебный патч/смещение для ветвления.

### 3. Форма слова словаря

Каждое слово имеет фиксированный layout:

1. `LINK` — ссылка на предыдущее слово.
2. `FLAGS` — биты immediate/hidden/kind.
3. `NAME_PTR` — адрес имени или токена имени.
4. `CODE` — execution token, то есть адрес кода слова.
5. `DATA` — адрес параметрического поля или данных слова.

Этот layout не менять по ходу проекта.

### 4. Строки и имена

Строки являются обычными объектами памяти:

1. `LEN` в одной ячейке.
2. затем `LEN` байтов полезной нагрузки.
3. затем выравнивание до `CELL_BITS`.

Имена слов словаря хранятся как строки этого же формата.

Это устраняет отдельный special case для имён и string literals.

### 5. Числа

Базовый числовой формат для Forth ядра: беззнаковая ячейка ширины `CELL_BITS`.

Знаковые операции допускаются позже как слой интерпретации того же бита.

Это устраняет блокер выбора “24/32/произвольная ширина” для первого ядра.

### 6. Управление тактом

Первый обязательный модуль не Forth, а минимальный in-space scheduler/loader, который:

- гарантирует, что в `PROCESSOR` всегда есть следующий такт;
- не допускает самопересечений копирований в пределах такта;
- умеет chain-load следующих страниц исполнения.

Без этого любой Forth будет нестабилен. Этот модуль реализуется раньше словаря.

### 7. Разделение hard и soft words

Hard words:

- реализованы непосредственно как страницы копирований;
- используются для bootstrap;
- не требуют уже работающего Forth.

Soft words:

- определяются поверх hard words;
- компилируются и расширяются уже самим Forth.

Это снимает блокер самохостинга.

### 8. Последовательность адресации

Очереди, общая машина Тьюринга и layer manager не входят в критический путь первого Forth.

Первый Forth использует только:

- прямую адресацию;
- стековую адресацию;
- возвратную адресацию;
- линейный аллокатор `HERE`.

## Execution Model

### 1. NEXT

`NEXT` делает только следующее:

1. Читает ячейку по `VAR_IP`.
2. Кладет адрес вызываемого слова в `VAR_W`.
3. Продвигает `VAR_IP` на одну ячейку.
4. Загружает страницу `CODE(VAR_W)` в `PROCESSOR`.

### 2. ENTER

Colon-word при входе:

1. кладет текущий `VAR_IP` в стек возвратов;
2. устанавливает `VAR_IP = DATA(VAR_W)`;
3. передает управление в `NEXT`.

### 3. EXIT

`EXIT`:

1. снимает адрес из стека возвратов;
2. записывает его в `VAR_IP`;
3. передает управление в `NEXT`.

### 4. EXECUTE

`EXECUTE`:

1. снимает xt со стека данных;
2. пишет его в `VAR_W`;
3. загружает `CODE(VAR_W)`;
4. не изменяет стек возвратов сам по себе.

### 5. LIT

`LIT`:

1. читает ячейку literal по `VAR_IP`;
2. продвигает `VAR_IP`;
3. кладет literal в стек данных;
4. возвращается в `NEXT`.

## Bootstrap Strategy Without Host Runtime

### Stage A: Static Boot Image

В пространство заранее зашивается boot image. Это не runtime-хостимость, а начальное состояние пространства, допустимое по `doc/adress_space.md`.

Boot image обязан содержать:

- scheduler/loader;
- hard words;
- фиксированные переменные;
- пустой или почти пустой словарь с kernel words;
- одну bootstrap-программу в `TOKEN_STREAM`.

### Stage B: First Internal Execution

После старта пространство:

1. загружает `NEXT`;
2. исполняет bootstrap-program из `TOKEN_STREAM`;
3. создает первые soft words;
4. переходит к self-hosted расширению словаря.

### Stage C: Internal Compiler Takes Over

Как только `:` `;` `FIND` `NUMBER?` `INTERPRET` готовы, дальнейшее расширение языка делается уже только через Forth.

Это обязательная граница. После нее новые runtime-mechanisms добавлять только если они действительно невыразимы на уже работающем Forth.

## Scheduler And Copy Safety Plan

Этот раздел убирает главный инженерный блокер: пересечение копирований и опустение `PROCESSOR`.

### Rule 1: Every Word Page Ends In Safe Chain-Load

Каждое hard word должно завершаться не “возвратом по договоренности”, а явной загрузкой следующей страницы такта.

### Rule 2: One Owner Per Destination Region Per Tick

До начала реализации все переменные и области разбиваются по владельцам такта. В одном такте одна область может иметь только одного писателя.

Минимальные группы:

- scheduler fields
- stack pointer fields
- stack cell writes
- dictionary writes
- heap writes
- scratch writes

### Rule 3: Read-Modify-Write Uses Scratch

Если операция требует вычисления нового значения указателя или флага, она обязана:

1. прочитать старое значение в scratch;
2. вычислить новое значение;
3. сделать единственную запись в основную переменную.

Это устраняет скрытые самопересечения.

### Rule 4: Pointer Updates Are Late Writes

Запись новых `SP`, `RP`, `IP`, `HERE`, `LATEST` выполняется в конце слова после завершения всех чтений старых значений.

### Rule 5: Multi-Cell Object Allocation Is Two-Phase

Для строк, словарных статей и буферов:

1. сначала вычисляется `new_here`;
2. затем выполняются все записи объекта в старом интервале `[HERE, new_here)`;
3. только затем `HERE := new_here`.

### Rule 6: Tick Optimizer Is Optional, Safety Is Mandatory

Оптимизация по `doc/copy_optimization.md` можно вводить позже. Но первый код обязан быть корректным без оптимизатора.

## Dictionary ABI

Фиксировать именно такой ABI:

1. ячейка `LINK`
2. ячейка `FLAGS`
3. ячейка `NAME_PTR`
4. ячейка `CODE_PTR`
5. ячейка `DATA_PTR`

Для colon-word:

- `CODE_PTR = ENTER`
- `DATA_PTR = address of first parameter cell`

Для primitive word:

- `CODE_PTR = address of primitive page`
- `DATA_PTR = 0` или служебный адрес по необходимости

Для variable:

- `CODE_PTR = code that pushes DATA_PTR`
- `DATA_PTR = address of storage cell`

Для constant:

- `CODE_PTR = code that pushes value from DATA_PTR`
- `DATA_PTR = address of stored literal cell`

Это заранее снимает блокер defining words.

## Value Model

Нужно довести план не до “минимума слов”, а до возможности выражать данные всех типов, нужных для дальнейшего саморазвития Forth.

### Supported Value Kinds

Минимально обязательны:

1. cell number
2. xt
3. data address
4. string address
5. buffer address
6. branch patch address

Все они имеют один physical format: значение в ячейке `CELL_BITS`.

Различие между ними только семантическое и задается словом-потребителем.

Это устраняет блокер tagged runtime. Теги не нужны в MVP.

## String Model

- первая ячейка: длина в байтах

### Required Early String Operations

- создать строку в heap
- скопировать строку
- сравнить две строки
- получить `addr len`
- записать строковый literal в словарь

### Decision

Не откладывать строки после токенового Forth. Их нужно добавить сразу после словаря и базового компилятора.

## Number Model

Числа тоже нельзя откладывать до “потом”.

### Base Support

Нужно ввести:

- `VAR_BASE`
- `DECIMAL`
- `HEX`

### Parser Contract

`NUMBER?` принимает `addr len` строки и возвращает:

- parsed value
- success flag

Первый parser обязан поддерживать:

- unsigned decimal
- unsigned hexadecimal with one fixed accepted form

Не добавлять signed, prefixes и bases beyond these until базовый parser стабилен.

Это убирает расползание scope.

## Input Model Without Host

Чтобы Forth дальше рос “силами самого Форта”, нужен внутренний источник текста.

### Fixed Decision

Вместо terminal input использовать `INPUT_BUFFER` внутри памяти.

Интерпретатор работает так:

1. получает `INPUT_BUFFER` как строку;
2. `WORD` выделяет следующее слово;
3. `FIND` ищет его в словаре;
4. если найдено:
- либо исполняет;
- либо компилирует в зависимости от `STATE` и immediate bit;
5. если не найдено:
- вызывает `NUMBER?`;
- при успехе либо кладет literal на стек, либо компилирует `LIT` + число;
6. при провале пишет код ошибки во внутренний status cell.

Это делает `INTERPRET` полностью внутренним и достаточным для саморазвития.

## Internal Error Model

Ошибки нужны сразу, иначе реализация дальше будет немой и труднорасширяемой.

Ввести фиксированные cells:

- `ERR_CODE`
- `ERR_ARG0`
- `ERR_ARG1`

Минимальные коды:

- `0` no error
- `1` stack underflow
- `2` stack overflow
- `3` return stack underflow
- `4` return stack overflow
- `5` word not found
- `6` bad number
- `7` dictionary overflow
- `8` heap overflow
- `9` compile structure mismatch

Первый интерпретатор обязан останавливать текущую операцию и оставлять код ошибки в этих cells.

Это устраняет блокер диагностики.

## Detailed Development Plan Before The Forth Implementation Plan

Этот раздел задает подробный план разработки каждого обязательного пункта, который должен существовать в пространстве до того, как Forth сможет устойчиво расти собственными средствами.

Порядок разделов обязателен. Если выполнять его сверху вниз, следующий раздел не должен требовать пересмотра предыдущего.

### A. Механизм, который не оставляет `PROCESSOR` пустым

**Назначение**

Обеспечить, что пространство не останавливается между тактами и что каждое primitive word гарантированно передает управление следующему такту.

**Что должно быть зафиксировано до кода**

- один fixed loader page;
- один fixed return path для primitive pages;
- одна область `PROCESSOR_FEED`;
- правило: ни одно primitive word не пишет в произвольные слоты `PROCESSOR`, кроме слотов, выделенных ему loader contract.
- ядро грузит начало образа прямо в `PROCESSOR`, а не в `REGISTER`;
- продолжение загрузки определяется уже загруженными инструкциями образа;
- образ может грузить не только следующие слои инструкций в `PROCESSOR`, но и данные в `REGISTER`;
- на этапе отладки последний слой образа останавливает пространство.

**Модель образа**

Образ состоит из:

1. последовательности слоёв инструкций копирования;
2. данных, которые эти слои должны загрузить в `REGISTER`;
3. при необходимости слоёв вывода диагностики.

Формат образа не фиксируется отдельным внешним контрактом. Он выбирается при проектировании самого образа так, чтобы каждому слою было удобно:

- знать, сколько инструкций следующего слоя нужно загрузить в `PROCESSOR`;
- знать, сколько данных нужно загрузить в `REGISTER`;
- знать адреса назначения для этих инструкций и данных;
- при необходимости настраивать инструкции вывода диагностики в `OUT`.

Начало образа определяется не отдельной таблицей, а адресом, на который указывает загрузчик.

Точка входа отдельно не задаётся: ядро загружает первый слой образа в `PROCESSOR`, исполняет его, а этот слой уже загружает следующий слой, нужные данные и при необходимости диагностику.

Конец образа на этапе отладки определяется последним слоем, который выключает пространство.

**Порядок разработки**

1. Зафиксировать номера слотов `PROCESSOR`, принадлежащих loader.
2. Зафиксировать поля этих слотов: какие задают адрес чтения из `IN`, какие задают адрес записи в `PROCESSOR`, какие задают адрес записи в `REGISTER`, какие задают длину копирования.
3. Зафиксировать, что ядро грузит только первый слой образа, а дальнейшие слои грузятся уже инструкциями образа.
4. Зафиксировать форму chain-load: слой не “возвращается”, а загружает следующий слой, который должен исполняться после него.
5. Зафиксировать правило слоёв: за один раз исполняется один слой, и он не может выходить за пределы `PROCESSOR`.
6. Зафиксировать правило размещения данных: слои могут читать из канала и класть данные либо в `PROCESSOR`, либо в `REGISTER`, но адреса и размеры должны быть заранее настроены в самом образе.
7. Зафиксировать диагностику загрузки: ядро и при необходимости каждый слой могут иметь одну или несколько инструкций вывода в `OUT`.
8. Зафиксировать один idle-safe path: если слой не делает полезной работы, он все равно подготавливает следующий исполнимый слой.
9. Реализовать базовую страницу loader для первого слоя.
10. Реализовать для каждого primitive page одинаковый хвост возврата в loader или в следующий слой образа по одному и тому же контракту.
11. Проверить, что без словаря и стеков loader уже может поддерживать пустой вычислительный цикл.
12. Проверить, что последний слой отладочного образа останавливает пространство.
13. Добавить active proof runner, который подает образ в `IN`, сохраняет `OUT` и при необходимости сохраняет дамп пространства после выполнения.

**Антиблокер**

- не вводить несколько независимых загрузчиков;
- не давать primitive words прямое владение всем `PROCESSOR`;
- не совмещать логику loader и логику словаря.
- не грузить весь образ сначала в `REGISTER`, если образ должен уметь менять сам загрузчик;
- не описывать образ как набор “кусков”: единица загрузки и исполнения здесь слой;
- не делать отдельную внешнюю точку входа поверх первого слоя образа.
- не фиксировать отдельный универсальный формат образа раньше, чем появится первый рабочий образ;
- не выносить диагностику загрузки за пределы самих слоёв, если её можно передавать через `OUT`.

**Готовность**

Раздел готов, когда ядро загружает первый слой образа в `PROCESSOR`, каждый слой загружает следующий слой и нужные данные, а отладочный последний слой останавливает пространство.

### B. Внутреннее threaded execution

**Готовность**

### D. Память как рабочая область языка

**Назначение**

**Что должно быть зафиксировано до кода**

- стартовый адрес `HERE`;
- границы словаря и heap;
- отдельная scratch area;

**Порядок разработки**

1. Зафиксировать границы всех областей.
2. Зафиксировать, что словарь растет в одном направлении, heap в одном направлении.
3. Зафиксировать `HERE` как единственный линейный аллокатор словаря и объектов.
4. Зафиксировать `TOKEN_STREAM` как внутренний bootstrap source.
5. Зафиксировать `INPUT_BUFFER` как будущий источник текста.
6. Зафиксировать `SCRATCH` как обязательную область для read-modify-write.

**Антиблокер**

- не смешивать token stream и input buffer;
- не вводить второй независимый аллокатор до завершения первого.

**Готовность**

Раздел готов, когда layout пространства позволяет развивать словарь и объекты без пересмотра адресов.

Раздел готов, когда есть устойчивые forward и backward переходы в потоке ячеек.

### M. Линейный порядок сборки без блокеров

Этот раздел связывает все предыдущие пункты в один обязательный порядок разработки.

1. `A` механизм удержания `PROCESSOR`
2. `B` threaded execution
3. `C` два стека
4. `D` layout рабочей памяти
5. `E` memory и arithmetic primitives
6. `L` правила безопасного копирования как gate для каждого нового primitive page
7. `G` ABI словаря
8. `F` ветвление
9. `H` строковый объект
10. `I` parser чисел
11. `K` error cells
12. `J` внутренний интерпретатор входного буфера

После этого только в таком порядке:

13. `CREATE VARIABLE CONSTANT VALUE TO BUFFER:`
14. `STATE [ ] COMPILE, : ;`
15. `IMMEDIATE HIDE REVEAL`
16. `IF ELSE THEN BEGIN UNTIL AGAIN WHILE REPEAT`
17. `S\" POSTPONE LITERAL ' ['] CHAR [CHAR]`
18. `TYPE COMPARE -TRAILING`
19. bootstrap-программа self-extension

Если этот порядок не нарушать, блокеров уровня архитектуры в плане не остается: все следующие механизмы опираются только на уже зафиксированные ABI, области памяти и primitives.

## Implementation Phases

### Phase 0: Freeze ABI And Layout

- [ ] Зафиксировать один layout памяти для `CORE_VARS`, стеков, словаря, heap, token stream, input buffer, scratch.
- [ ] Зафиксировать width ячейки: `CELL_BITS = ADDR_BITS`.
- [ ] Зафиксировать dictionary ABI из этого плана.
- [ ] Зафиксировать формат строки `LEN + BYTES + ALIGN`.
- [ ] Зафиксировать формат флагов `FALSE=0`, `TRUE=all-ones`.
- [ ] Зафиксировать error cells и коды ошибок.

**Exit criterion:** Ни один следующий этап не требует пересмотра layout или ABI.

### Phase 1: Build Safe Scheduler/Loader

- [ ] Поднять минимальный in-space loader, который всегда загружает следующий такт в `PROCESSOR`.
- [ ] Зафиксировать цепочку возврата всех primitive pages в loader.
- [ ] Разделить ownership областей записи по тикам.
- [ ] Проверить, что ни одно primitive word не оставляет `PROCESSOR` пустым.
- [ ] Проверить, что указатели записываются только поздней записью.

**Exit criterion:** Пространство может бесконечно исполнять bootstrap-cycle без помощи хоста.

### Phase 2: Build Execution Kernel

- [ ] Реализовать `NEXT`.
- [ ] Реализовать `ENTER`.
- [ ] Реализовать `EXIT`.
- [ ] Реализовать `EXECUTE`.
- [ ] Реализовать `LIT`.
- [ ] Проверить вызов primitive word и colon-word.

**Exit criterion:** Исполняется цепочка из primitive и colon words.

### Phase 3: Build Two Stacks

- [ ] Реализовать `DPUSH/DPOP`.
- [ ] Реализовать `RPUSH/RPOP`.
- [ ] Реализовать `DUP DROP SWAP OVER`.
- [ ] Реализовать `>R R> R@`.
- [ ] Ввести проверки underflow/overflow через error cells.

**Exit criterion:** Вложенные вызовы и обычные стековые слова работают стабильно.

### Phase 4: Build Memory And Arithmetic Core

- [ ] Реализовать `@ ! C@ C!`.
- [ ] Реализовать `, C, ALLOT`.
- [ ] Реализовать `1+ 1- + -`.
- [ ] Реализовать `AND OR XOR INVERT`.
- [ ] Реализовать `0= = < U<`.
- [ ] Реализовать `CELL+ CELLS COUNT MOVE FILL`.

**Exit criterion:** Есть полный базовый набор для адресов, данных и объектов переменной длины.

### Phase 5: Build Dictionary And Defining Kernel

- [ ] Реализовать `HERE@ HERE!`.
- [ ] Реализовать `LATEST@ LATEST!`.
- [ ] Реализовать `CREATE-HEADER`.
- [ ] Реализовать `NAME>XT XT>DATA`.
- [ ] Реализовать primitive-level `FIND-NAME`.
- [ ] Реализовать `CREATE VARIABLE CONSTANT VALUE TO BUFFER:`.

**Exit criterion:** Пространство может само создавать словарные статьи и объектные слова.

### Phase 6: Build Compiler Core

- [ ] Реализовать `STATE@ STATE! [ ]`.
- [ ] Реализовать `COMPILE,`.
- [ ] Реализовать `:`.
- [ ] Реализовать `;`.
- [ ] Реализовать `IMMEDIATE`.
- [ ] Реализовать `HIDE` и `REVEAL`.
- [ ] Проверить, что новые colon-words определяются уже внутри пространства.

**Exit criterion:** Self-hosted определение слов работает.

### Phase 7: Build Control Structures

- [ ] Реализовать `BRANCH`.
- [ ] Реализовать `0BRANCH`.
- [ ] Реализовать compile-time patching для forward branches.
- [ ] Реализовать `IF ELSE THEN`.
- [ ] Реализовать `BEGIN UNTIL AGAIN WHILE REPEAT`.
- [ ] Реализовать диагностику mismatch в `ERR_CODE`.

**Exit criterion:** Внутренний компилятор поддерживает обычные управляющие конструкции.

### Phase 8: Build String Objects Early

- [ ] Реализовать `S,`.
- [ ] Реализовать `SCOPY`.
- [ ] Реализовать `S=`.
- [ ] Реализовать `addr len` extraction из string object.
- [ ] Реализовать хранение имён слов как обычных строк.
- [ ] Реализовать string literal compilation для будущего `S"`.

### Phase 9: Build Number Parsing

- [ ] Ввести `VAR_BASE`.
- [ ] Реализовать `DECIMAL`.
- [ ] Реализовать `HEX`.
- [ ] Реализовать `NUMBER?` для unsigned decimal.
- [ ] Реализовать `NUMBER?` для unsigned hexadecimal в одном фиксированном формате.
- [ ] Проверить поведение при ошибке разбора.

**Exit criterion:** Интерпретатор сможет принимать числа из строк.

### Phase 10: Build Internal Text Interpreter

- [ ] Реализовать `WORD` поверх `INPUT_BUFFER`.
- [ ] Реализовать пользовательский `FIND`, опирающийся на строковые имена.
- [ ] Реализовать `'` и `[']`.
- [ ] Реализовать `CHAR` и `[CHAR]`.
- [ ] Реализовать `INTERPRET`.
- [ ] Реализовать `EVALUATE` для строки из памяти.

**Exit criterion:** Пространство может получать строку из своей памяти и интерпретировать ее как Forth.

### Phase 11: Build String Literals And Expansion Tools

- [ ] Реализовать `S"`.
- [ ] Реализовать `POSTPONE`.
- [ ] Реализовать `LITERAL`.
- [ ] Реализовать `TYPE` как запись в внутренний output buffer.
- [ ] Реализовать `COMPARE` и `-TRAILING`.

**Exit criterion:** Язык уже удобен для дальнейшего роста силами самого Forth.

### Phase 12: Build Self-Extension Baseline

- [ ] Подготовить bootstrap-программу, которая сама определяет несколько soft words поверх уже работающего ядра.
- [ ] Проверить, что после этого можно добавлять новые слова только через `EVALUATE` и внутренний буфер.
- [ ] Перевести дальнейшее расширение на self-hosted path.

**Exit criterion:** Дальнейшее развитие Forth возможно без добавления новых host-side механизмов.

## Minimal Milestone Set

### Milestone 1

Пространство живет само и удерживает `PROCESSOR`.

### Milestone 2

Работают `NEXT`, два стека и primitive words.

### Milestone 3

Словарь создается и растет внутри пространства.

### Milestone 4

Работают `:` и `;`, то есть Forth уже self-defining.

### Milestone 5

Работают строки и parser чисел.

### Milestone 6

Работает `INTERPRET` над `INPUT_BUFFER`.

### Milestone 7

Работает `EVALUATE`; язык дальше расширяет сам себя.

## Blockers Eliminated By This Plan

Этот план специально закрывает все типовые блокеры заранее.

### Blocker: нет безопасного следующего такта

Решение: scheduler/loader идет раньше любого Forth semantics.

### Blocker: непонятен формат словаря

Решение: dictionary ABI зафиксирован заранее.

### Blocker: непонятно, как хранятся строки

Решение: единый string object format зафиксирован заранее.

### Blocker: непонятно, как язык начнет понимать числа

Решение: `NUMBER?` и `VAR_BASE` встроены до текстового интерпретатора.

### Blocker: непонятно, как перейти от токенового режима к текстовому

Решение: сначала boot token stream, потом string objects, потом `WORD/FIND/NUMBER?/INTERPRET`.

### Blocker: непонятно, как отлаживать ошибки

Решение: фиксированные `ERR_*` cells вводятся с самого начала.

### Blocker: пересекающиеся копирования

Решение: ownership by region, late pointer writes, two-phase allocation, scratch-based RMW.

### Blocker: defining words потребуют нового ABI

Решение: `VARIABLE`, `CONSTANT`, `VALUE`, `BUFFER:` уже выражены через один и тот же dictionary ABI.

## Non-Goals For This Plan

- Общая машина Тьюринга.
- Очередь как обязательный runtime primitive.
- Канальный ввод-вывод.
- Полный ANS Forth.
- Многозадачность.
- layer manager.
- оптимизация копирований как prerequisite к корректности.

## Final Decision

План доводит систему не просто до “минимального Форта”, а до self-hosted ядра со значениями, строками, числами, именованным словарем и внутренним интерпретатором строкового буфера. После завершения этого плана дальнейшее расширение языка, библиотек, редактора и shell должно идти уже средствами самого Forth, не упираясь в хост и не требуя пересмотра базовой архитектуры.
