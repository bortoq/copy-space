# GCC внутри пространства

Цель: GCC исполняет препроцессирование и компиляцию C внутри пространства,
принимает исходники и заголовки через IN и выдаёт через OUT программу
прямых копирований. Линковка результата также выполняется внутри
пространства. Готовые программы выполняются копированиями без RV32.
Эмулятор хоста содержит только существующие примитивы и каналы.

Начальный образ GCC разрешено подготовить на хосте. Сам GCC первоначально
может работать на существующем RV32I, исполняемом копированиями внутри
пространства. Компиляция пользовательского задания хостовым GCC,
хостовая интерпретация промежуточного кода и выполнение результата через
RV32 не являются завершением этой цели. Сборка самого GCC из исходников
внутри пространства — отдельная последующая задача.

Начальная версия — GCC 12.5.0: последний исправленный выпуск серии 12,
для которой уже выполнены контрольные проверки Linux 6.12 с GCC 12.3.
Версия закрепляется исходным архивом и официальной SHA-512; дополнительно
сохраняется SHA-256. GCC 12.5 требует C++11 при подготовке самого
компилятора. Это не требование C++ к исходникам ядра.
Источники: https://gcc.gnu.org/gcc-12/,
https://gcc.gnu.org/pub/gcc/releases/gcc-12.5.0/sha512.sum,
https://gcc.gnu.org/install/prerequisites.html.

Все исходники, зависимости, подготовительные сборки и сырые доказательства
хранятся в `/media/user/data/work`, вне системного диска и Git. Выполнять
крупные операции по одной, с `nice -n 15` и `ionice -c 3`. Проверять архивы
до распаковки; фиксировать версии, команды, размеры и контрольные суммы.

Исходный GCC проверен: 85897368 байтов, SHA-256
`71cd373d0f04615e66c5b5b14d49c1a4c1a08efa7b30625cd240b11bab4062b3`.
Начальная распаковка содержит 20641 запись; 101488 записей testsuite пока
не распакованы для снижения нагрузки на диск. Для сборки libstdc++ затем
восстановлены 37 шаблонов `.in` из testsuite; скрипт сохраняет их при новой
распаковке. Полный архив сохранён.
Повторяемая подготовка — `scripts/gcc/fetch.py --store DIR --extract`.

GMP 6.2.1, MPFR 4.1.0 и MPC 1.2.1 выбраны по собственному
`contrib/download_prerequisites` GCC 12.5; архивы сверены с его SHA-512.
Начальная гостевая libc — newlib 4.5.0.20241231; первоначальная загрузка
выполнена с HTTPS upstream, затем закреплена SHA-256
`33f12605e0054965996c25c1382b3e463b0af91799001f5bb8c0630f2ec8c852`.
Для newlib независимая опубликованная контрольная сумма не проверена;
не приравнивать эту первоначальную фиксацию к проверке SHA-512 GCC.
Гостевые библиотеки собираются RV32I/ILP32, одним заданием Make, без
libgloss и его обращений к хостовой ОС. Стандартные функции newlib
получают операции памяти и файлов от нашей гостевой библиотеки.
Подготовка newlib ещё не доказывает работу GCC.

Начальная проверка гостевой libc использует ограниченную кучу и потоки
stdin/stdout поверх существующих cs_read/cs_write. Затем подключены
гостевые файловые операции, описанные ниже. Загрузка задания GCC и его
аргументов через каналы остаётся обязательной. Куча должна
сохранять состояние при отказе и обеспечивать 16-байтовое выравнивание
для long double RV32. В newlib явно задаётся `MALLOC_ALIGNMENT=16`.
При подключении newlib функции memcpy/memmove/memset/memcmp предоставляет
она; существующий runtime RV32I отключает собственные версии только по
`CS_RUNTIME_EXTERNAL_MEMORY`. Без этого флага прежние сборки сохраняются.
В configure не удалять неиспользуемые секции: без настоящего стартового
кода это может удалить проверяемую ссылку и ложно объявить функцию
доступной. Статические библиотеки зависимости и libc линковать группой.

Файловая среда GCC принимает существующий CCFILES1: до 1024 входных
файлов, имена до 4096 байтов. Исходный буфер остаётся жив до завершения
задания; входные файлы доступны только для чтения. Создаваемые выходные
файлы принадлежат гостевой куче и допускают чтение, запись, append,
truncation и seek. До 64 одновременно открытых дескрипторов; 0..2
зарезервированы потоками. Пути разрешаются от виртуального корня, с
нормализацией /, . и ..; выхода выше корня нет. Каталоги входных файлов
определяются по именам. Не обращаться к open/stat ОС хоста.

Проверены два исполнения обычным эмулятором пространства: стандартные
функции newlib — 13028010 копирований, OUT `gcc-libc:7:15:4294967303\n`;
файловые операции — 178749262 копирования, OUT `gcc-files:7\n`.
В обоих случаях гостевой код завершился с 0, весь OUT совпал с нативным
эталоном. Проверены ошибки кучи, нормализация путей, права входных файлов,
seek и заполнение промежутков нулями, append/truncation, unlink открытого
файла, предел дескрипторов, сохранение состояния при неверном пакете,
а также fopen/fread/fwrite/fclose newlib. Сырые журналы, дампы и SHA-256
сохранены в `copy-space-artifacts/space-tests/gcc-newlib-stdlib-native-memory`
и `copy-space-artifacts/space-tests/gcc-newlib-files` на data/work.
Это доказательство гостевой библиотеки, не исполнения GCC.

GMP, MPFR, MPC, libstdc++ 12.5 и libsupc++ подготовлены для RV32I/ILP32.
Первоначальный подготовительный GCC 10.2 не поддерживал использованные
встроенные функции C++; сборка libstdc++ завершена новым GCC 12.2.
Архивы закреплены SHA-256 в `libraries.json` подготовительной сборки.
Готовность cc1 этим этапом не подтверждается. Для подготовки
выбран отдельный GCC 12.2 и binutils 2.40 из Debian bookworm: пакеты
распаковываются на data/work без установки в систему, SHA-256 сверяется
с опубликованными значениями packages.debian.org. Старый компилятор
сохраняется для воспроизведения прежних проверок.
GCC 12.2 и binutils 2.40 загружены, суммы совпали, распаковка завершена
и запуск нового компилятора проверен.

Задание GCC передаётся пакетом `GCCJOB1`: восемь байтов `GCCJOB1\0`,
затем little-endian uint32 argc и размер вложенного CCFILES1. Далее для
каждого аргумента — uint32 длина и байты без NUL; в конце — CCFILES1.
Пределы: 256 аргументов, 4096 байтов каждый, весь пакет до 16 МиБ.
Первый аргумент — имя программы, пустые последующие допустимы. Разбор,
выделение argv и подключение файлов выполняются гостевым C; буфер пакета
сохраняется до завершения задания. Повреждённый пакет не заменяет файлы
текущего задания. Код разборщика не компилирует исходники на хосте.
Чтение задания из IN проверено обычным эмулятором: весь OUT `gcc-job:7\n`
совпал с нативным эталоном, гостевой код завершения 0. Полные журналы,
дампы и закреплённые исходники находятся на data/work в
`copy-space-artifacts/space-tests/gcc-newlib-job-channel`.

Подготовка cc1 использует разные build и host: генераторы GCC исполняются
нативно на хосте подготовки, cc1 и его зависимости собираются RV32I/ILP32.
Первый контрольный target также RV32I; он будет заменён генератором
копирований после проверки настоящего cc1 внутри пространства. Начальный
скрипт собирает `all-gcc`, без bootstrap, LTO, Graphite, NLS и целевых
библиотек. Это не отключает обязательную семантику GNU C. Все команды
configure/make, ошибки и коды завершения сохраняются на data/work.
Для исполнения C++-кода нужен отдельный гостевой старт newlib:
инициализация preinit/init arrays перед main, регистрация fini arrays и
завершение через exit для вызова деструкторов. Эти операции выполняет
гостевой код, эмулятор не получает C++-функций. Прежний freestanding старт
остаётся доступен для остальных образов.
Порядок constructor → main → atexit → destructor проверен в пространстве:
1717409 копирований, весь OUT совпал с нативным эталоном, код завершения 0.
Доказательства на data/work: `copy-space-artifacts/space-tests/gcc-newlib-initializers-gcc12`.

Порядок переноса:

1. Закрепить GCC, определить действительные зависимости и подготовить
   исходники. Зафиксировать различие архитектуры подготовки, исполнения
   компилятора и результата; не смешивать библиотеки этих архитектур.
2. Подготовить гостевую библиотеку памяти, файлов и аргументов. Файлы
   задания хранятся внутри гостя; open/read/seek/write/stat работают с
   ними без обращения к файловой системе хоста после загрузки через IN.
   Ошибки и диагностика возвращаются через OUT. Не добавлять системные
   вызовы файловой системы или C-операции в эмулятор пространства.
3. Собрать настоящий cc1 для RV32I/ILP32, с необходимыми библиотеками;
   исключить обязательное исполнение неподдерживаемых инструкций.
   Первоначальный существующий RISC-V генератор нужен только для
   контрольного запуска компилятора. Он не заменяет генератор копирований.
4. Запустить препроцессирование и контрольную компиляцию GCC внутри
   пространства. Сохранить исходник, IN/OUT, образы, параметры размещения,
   полный сырой журнал, код завершения и контроль результата.
5. Реализовать цель прямых копирований GCC: размещение типов, операции,
   вызовы, аргументы, возвраты, адреса функций, секции и перемещения.
   Использовать имеющиеся проверенные операции как основу и эталон;
   не подменять GNU C разбором нынешнего Forth-подмножества.
6. Реализовать гостевую линковку и загрузку результата. Проверить отдельно
   раздельную компиляцию, адреса внешних функций и общий ABI.
7. Доказать сквозное исполнение GNU C: IN с исходниками → GCC внутри
   пространства → OUT с программой → прямое исполнение программы.
   Повторить существенные макросы и выбранные единицы Linux 6.12 NOMMU.

Нынешнее размещение допускает до 256 МиБ пространства и 64 МиБ гостевой
памяти RV32I. Достаточность для GCC ещё не измерена; выбирать размещение
по размеру настоящего ELF, статических объектов, стека и расходу кучи.
Лимит 2 МиБ нынешнего прямого результата C также требует отдельного
расширения. Ни один промежуточный этап не означает завершение переноса.
