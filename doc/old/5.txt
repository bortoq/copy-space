3) Реализованные бенчи
3.1 PACK (gather → pack)
Генератор образа создаёт K слотов, каждый копирует chunk из “разреженного” src (stride) в “плотный” dst.
Поддержка random mapping (перемешивание src chunk index при сохранении dst non-overlap).
3.2 PERMUTE (chunk permutation)
K слотов, src и dst оба “плотные”, но src chunk выбирается по перестановке:
reverse
random (seed)
(в генераторе возможен bitrev).
4) Полученные результаты пользователя (PACK/PERMUTE)
Параметры:

COPIES=64
CHUNK_BYTES=1024
(PACK) SRC_STRIDE_BYTES=4096
MODE: PACK / PACK random / PERMUTE reverse / PERMUTE random
Результат (во всех случаях одинаковый):

avg_bits_sum_per_tick = 524288
avg_bits_uniq_dst_per_tick = 524288
sum == uniq (нет overlap по dst)
throughput окно совпадает с latency
То есть 64 слота * 1024 bytes/slot = 65536 bytes/tick = 524288 bits/tick.

5) Интерпретация ассистента: насколько это “впечатляюще”
5.1 Технически это хороший знак
Метрики сходятся с ожидаемыми (архитектурная корректность бенчей).
sum == uniq показывает отсутствие коллизий записи (соответствует инварианту).
5.2 Но как “вау-демо” — пока слабовато
Причины:

Все режимы дают один и тот же потолок (64 слота × 1KB) ⇒ мы измерили “верхний предел описуемой за тик работы” в текущем ISA/PROCESSOR_N.
Нет сравнения с “тонкими” словами (EQ24P), нет контраста.
Нет sweep по параметрам (кривых/таблицы), только одна точка.
Нет baseline сравнения с CPU (memcpy/gather).
5.3 Главный смысл результата
В copyspace модель “стоимость произвольной перестановки чанков” ≈ “стоимость bulk copy того же объёма” — это и есть ядро тезиса deterministic permutation fabric.
Но это нужно оформить как графики/контраст/сравнение.
