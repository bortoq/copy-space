# Устройства и каналы: device≠channel, менеджер каналов, гест-пространства как устройства

Этот документ фиксирует дизайн, в котором:
- **device** (устройство) — это уникальный объект с идентичностью и набором портов,
- **channel** (канал) — это порт/endpoint устройства с протоколом обмена,
- “другое пространство” (guest) рассматривается как устройство,
- взаимодействие с устройствами/гестами упорядочено через channel manager,
- детерминизм обеспечивается тем, что каналы — часть состояния space (и/или записываемый протокол).

## 1) Цели дизайна
1) Отделить device от channel: терминал с 1 input и 2 output — это **одно устройство**, а не “3 независимых канала”.
2) Location transparency: прикладному коду всё равно, обслуживает ли порт:
- внешний эмулятор/хост,
- внутренний гест,
- другой узел.
3) Возможность “оформить любую логику как изолированное пространство”, не превращая всё в дорогие копирования:
- поддержка zero-copy соглашений (передача указателей/прав).
4) Вынести “работу с устройствами” в отдельную логику (manager), отделив от прикладных вычислений.

## 2) Определения
- **Local memory**: “свои позиции” (регионы, принадлежащие модулю).
- **Device**: self-describing объект (type, version, device_id, ports).
- **Channel**: endpoint порта устройства (handshake + буфер/указатель).
- **Manager**: привилегированная логика, которая:
  - маршрутизирует сообщения по каналам,
  - выполняет цензуру и проверку границ,
  - реализует мост между пространствами/устройствами.

## 3) Device object и доказательство “порты принадлежат одному устройству”
Базовая идея: публиковать не 3 канала, а 1 device descriptor, который перечисляет порты.

### 3.1 Device Descriptor (желательно RO-регион)
`DEV_DESC` содержит:
- magic/version
- dev_type
- device_id (уникальный instance id)
- port_count
- массив `ports[]`: (port_id, chan_base, proto_id, flags)

Чтобы “доказательство принадлежности портов одному устройству” было строгим, descriptor должен быть:
- read-only для unprivileged кода (через цензуру менеджера или отдельный RO-регион).

### 3.2 Channel Header
Каждый `CHAN` содержит:
- magic/version
- device_id (ссылка на device)
- port_id
- proto fields (req/done/err/seq/len/buf_ptr и т.п.)

Верификация принадлежности:
- `chan.device_id == dev.device_id`
- `chan.port_id` присутствует в `dev.ports[]`
- `chan_base` совпадает с адресом, указанным в `dev.ports[]`

## 4) Протокол канала (минимальный, детерминированный)
Минимальный mailbox:
- `REQ` (writer->reader)
- `DONE/ACK` (reader->writer) или сброс REQ reader-ом
- `ERR`
- `SEQ` (монотонный счётчик, защита от tearing)
- `LEN`
- `BUF_PTR` (указатель на payload) либо inline payload буфер

Рекомендованный порядок:
- writer пишет payload, затем LEN/SEQ, затем REQ=1 (commit)
- reader читает REQ, затем SEQ/LEN/payload, затем REQ=0 (ack)

## 5) Гест-пространство как устройство
Гест оформляется как device:
- ports: например `CMD_IN` (host->guest), `RESP_OUT` (guest->host), и/или “grant” порт для zero-copy.
- guest читает свои входные порты и пишет в свои выходные порты, но **не имеет** прямого доступа к host memory.

Host/manager обслуживает guest:
- читает/пишет каналы,
- выполняет гостевые операции (копирования) только после цензуры.

## 6) Zero-copy соглашения (снятие потерь на каналах)
Чтобы не копировать payload через промежуточные буферы:
- каналы передают не данные, а **указатели/права** (grant/capability).
- manager проверяет владение/границы и “передаёт право” на интервал другому модулю.
- прикладной код остаётся “канальным”, а данные не копируются.

## 7) Где размещать device/channel структуры
Чтобы не ломать baseline MMIO и не двигать `workspace_base`, рекомендуется:
- не расширять MMIO в `space.c` без крайней необходимости,
- размещать device/channel структуру в выделенном “bus/io region” внутри workspace,
- публиковать базу bus через ART (одна запись `BUS_BASE` или `DEV_TABLE_BASE`).

## 8) План внедрения (MVP)
1) Определить bus region и добавить один `DEV_DESC` для TERM0.
2) TERM0: либо 3 порта (stdin/stdout/stderr), либо 1 порт с `stream_id`.
3) Сделать enumerator/validator в Forth0:
- найти dev_desc,
- проверить magic/version/device_id,
- получить chan_base по port_id.
4) Реализовать channel manager минимально:
- обработка REQ/DONE/SEQ,
- цензура границ для гостевых запросов.
5) Добавить тест “device discovery + channel exchange”.

## 9) Критерии корректности/детерминизма
- При фиксированном входе и начальном image результаты детерминированы.
- Каналы не зависят от внешней недетерминированной среды (если есть внешняя среда — ввод должен быть через протокол, который можно record/replay).
- Валидатор устройств проверяет self-consistency (device_id/ports/channel headers).
