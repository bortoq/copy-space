# GCC внутри пространства

Цель: GCC исполняет препроцессирование и компиляцию C внутри пространства,
принимает исходники и заголовки через IN и выдаёт через OUT программу
прямых копирований. Линковка результата также выполняется внутри
пространства. Готовые программы выполняются копированиями без RV32.
Эмулятор хоста содержит только существующие примитивы и каналы.

Начальный образ GCC разрешено подготовить на хосте. Сам GCC первоначально
может работать на существующем RV32I, исполняемом копированиями внутри
пространства. Компиляция пользовательского задания хостовым GCC,
хостовая интерпретация промежуточного кода и выполнение результата через
RV32 не являются завершением этой цели. Сборка самого GCC из исходников
внутри пространства — отдельная последующая задача.

Начальная версия — GCC 12.5.0: последний исправленный выпуск серии 12,
для которой уже выполнены контрольные проверки Linux 6.12 с GCC 12.3.
Версия закрепляется исходным архивом и официальной SHA-512; дополнительно
сохраняется SHA-256. GCC 12.5 требует C++11 при подготовке самого
компилятора. Это не требование C++ к исходникам ядра.
Источники: https://gcc.gnu.org/gcc-12/,
https://gcc.gnu.org/pub/gcc/releases/gcc-12.5.0/sha512.sum,
https://gcc.gnu.org/install/prerequisites.html.

Все исходники, зависимости, подготовительные сборки и сырые доказательства
хранятся в `/media/user/data/work`, вне системного диска и Git. Выполнять
крупные сборки по одной, с `nice -n 15` и `ionice -c 3`. Длительная
проверка пространства может продолжаться одновременно с одной сборкой
Make -j1, когда доступно не менее 8 ГиБ памяти; новые крупные загрузки
и распаковки при этом не запускать. Проверять архивы
до распаковки; фиксировать версии, команды, размеры и контрольные суммы.

Гостевые библиотеки собираются RV32I/ILP32, одним заданием Make, без
libgloss и его обращений к хостовой ОС. Стандартные функции newlib
получают операции памяти и файлов от нашей гостевой библиотеки.
Подготовка newlib ещё не доказывает работу GCC.

Начальная проверка гостевой libc использует ограниченную кучу и потоки
stdin/stdout поверх существующих cs_read/cs_write. Затем подключены
гостевые файловые операции, описанные ниже. Загрузка задания GCC и его
аргументов через каналы остаётся обязательной. Куча должна
сохранять состояние при отказе и обеспечивать 16-байтовое выравнивание
для long double RV32. В newlib явно задаётся `MALLOC_ALIGNMENT=16`.
При подключении newlib функции memcpy/memmove/memset/memcmp предоставляет
она; существующий runtime RV32I отключает собственные версии только по
`CS_RUNTIME_EXTERNAL_MEMORY`. Без этого флага прежние сборки сохраняются.
В configure не удалять неиспользуемые секции: без настоящего стартового
кода это может удалить проверяемую ссылку и ложно объявить функцию
доступной. Статические библиотеки зависимости и libc линковать группой.

Файловая среда GCC принимает существующий CCFILES1: до 1024 входных
файлов, имена до 4096 байтов. Исходный буфер остаётся жив до завершения
задания; входные файлы доступны только для чтения. Создаваемые выходные
файлы принадлежат гостевой куче и допускают чтение, запись, append,
truncation и seek. До 64 одновременно открытых дескрипторов; 0..2
зарезервированы потоками. Пути разрешаются от виртуального корня, с
нормализацией /, . и ..; выхода выше корня нет. Каталоги входных файлов
определяются по именам. Не обращаться к open/stat ОС хоста.
Просмотр каталогов для libcpp также гостевой: собственный dirent.h,
opendir/readdir/closedir перечисляют непосредственные дочерние имена
загруженных и созданных файлов. Повторные неявные подкаталоги возвращаются
один раз; открытый каталог запрещает замену смонтированного задания.
Гостевой заголовок подключается только RV32-драйвером подготовки.
Для линковки cc1 также нужны access/sysconf/gettimeofday. access проверяет
гостевые файлы: входные доступны для чтения, выходные — для записи;
файлы не имеют права исполнения, каталоги доступны для поиска и создания
выходных файлов. sysconf сообщает объём памяти гостя, оставшуюся часть
гостевой кучи, страницу 4096 байтов, 64 дескриптора и один процессор.
Неизвестные запросы завершаются EINVAL. gettimeofday использует гостевой
логический счётчик микросекунд; он служит детерминированной диагностике
GCC, не измеряет реальное время хоста. Эти функции исполняются копированиями.
libcpp открывает исходники с O_NOCTTY вместе с O_RDONLY/O_BINARY.
O_NOCTTY принимается без дополнительного действия: гостевые файлы
не становятся управляющим терминалом. Неизвестные флаги по-прежнему
отвергаются. Реальный первый запуск дошёл до этого вызова и выявил
его отказ EINVAL; файл и весь журнал сохранены, успехом он не считается.

Задание GCC передаётся пакетом `GCCJOB1`: восемь байтов `GCCJOB1\0`,
затем little-endian uint32 argc и размер вложенного CCFILES1. Далее для
каждого аргумента — uint32 длина и байты без NUL; в конце — CCFILES1.
Пределы: 256 аргументов, 4096 байтов каждый, весь пакет до 16 МиБ.
Первый аргумент — имя программы, пустые последующие допустимы. Разбор,
выделение argv и подключение файлов выполняются гостевым C; буфер пакета
сохраняется до завершения задания. Повреждённый пакет не заменяет файлы
текущего задания. Код разборщика не компилирует исходники на хосте.
Гостевая обёртка main читает этот пакет и передаёт argc/argv настоящему
main cc1 через линкерный `--wrap=main`. Буфер сохраняется до завершения
процесса для входных файлов и аргументов. Первое контрольное задание
использует `-E` и stdout; экспорт отдельных выходных файлов и диагностики
ещё требуется для полного интерфейса компиляции.
Ответ GCC может передаваться пакетом `GCCOUT1`: восемь байтов `GCCOUT1\0`,
затем little-endian uint32 код завершения, длины stdout, stderr и
выходного файла; далее три соответствующих массива байтов. Файл берётся
из гостевой файловой системы только при успешном завершении. Диагностика
сохраняется отдельно от результата. Формирование ответа и буферизация
потоков выполняются гостевым C; хост только обслуживает OUT эмулятора.
В режиме ответа имя экспортируемого файла задаётся первым аргументом
после имени программы: `--space-result=result.s`. Только этот служебный
аргумент удаляется перед вызовом cc1; все параметры GNU C сохраняются.
Он независим от GNU `-o`, который также должен указывать нужный файл.
Без служебного аргумента экспортируются только stdout/stderr; значение
`-` обозначает stdout. Разбирать остальные параметры GCC своим кодом нельзя.
Общий предел захваченных stdout/stderr — 16 МиБ, ошибки записи возвращаются
вызывающему коду. Этот пакет предназначен для гостевого следующего этапа;
готовый установочный пакет копирований остаётся конечным результатом.
Гостевой разборщик GCCOUT1 возвращает представления трёх блоков без
копирования их данных. Он проверяет все длины, общий предел потоков,
отсутствие лишних байтов и запрет выходного файла при ошибке GCC.
При отказе результат вызывающей стороны остаётся неизменным; исходный
буфер должен жить до завершения использования представлений. Это
интерфейс для будущего гостевого ассемблера/линкера, не сам линкер.

Подготовка cc1 использует разные build и host: генераторы GCC исполняются
нативно на хосте подготовки, cc1 и его зависимости собираются RV32I/ILP32.
Первый контрольный target также RV32I; он будет заменён генератором
копирований после проверки настоящего cc1 внутри пространства. Начальный
скрипт собирает зависимости и цель `gcc/cc1`, без bootstrap, LTO, Graphite, NLS и целевых
библиотек. Это не отключает обязательную семантику GNU C. Все команды
configure/make, ошибки и коды завершения сохраняются на data/work.
Гостевые библиотеки не передаются общим LIBS: GCC наследует его также
при настройке нативных генераторов. Подготовительные обёртки CC/CXX
подключают гостевые библиотеки только при линковке гостевого кода;
нативные CC_FOR_BUILD/CXX_FOR_BUILD используют системные библиотеки.
`all-gcc` также потребовал fixincludes с fork/exec/pipe; это утилита
подготовки системных заголовков, а не часть cc1. Не переносить её и
драйвер запуска ассемблера ради контрольного запуска C-препроцессора:
входные заголовки предоставляет пакет задания. Зависимости берутся из
исходной цели `cc1` GCC; функции GNU C в самом cc1 сохраняются.
Для быстрой диагностики гостевого ELF допускается отдельный QEMU user
для RV32I. Он не входит в рабочий запуск пространства и не заменяет
сырой журнал копирований. Пакет qemu-user-static 7.2+dfsg-5ubuntu2.4
из локального APT-каталога распаковывается только на data/work, SHA-256
`f90c421be6e68de5110c17de1b95314cb58cfc7750247581415b0aa15895da9d`.
Системная установка и binfmt-регистрация не нужны. Его результаты
фиксируются только как диагностический эталон с отдельным указанием области.
Исходный ELF с входом 0 QEMU не загрузил. Скрипт
`scripts/gcc/diagnose_guest.py` перелинковывает отдельный диагностический

суммы, пакет задания, OUT и системные обращения. Пакет передаётся в IN
без потока начальной загрузки пространства. Диагностический ответ GCCOUT1
проверяется целиком; он не является доказательством исполнения копированиями.

При прямом вызове Makefile gcc явно передаются CC_FOR_BUILD/CXX_FOR_BUILD

объектов нельзя. Это оптимизация самого компилятора, не задания пользователя.

гостевой код, эмулятор не получает C++-функций. Прежний freestanding старт
остаётся доступен для остальных образов.

Порядок переноса:

1. Закрепить GCC, определить действительные зависимости и подготовить
   исходники. Зафиксировать различие архитектуры подготовки, исполнения
   компилятора и результата; не смешивать библиотеки этих архитектур.
2. Подготовить гостевую библиотеку памяти, файлов и аргументов. Файлы
   задания хранятся внутри гостя; open/read/seek/write/stat работают с
   ними без обращения к файловой системе хоста после загрузки через IN.
   Ошибки и диагностика возвращаются через OUT. Не добавлять системные
   вызовы файловой системы или C-операции в эмулятор пространства.
3. Собрать настоящий cc1 для RV32I/ILP32, с необходимыми библиотеками;
   исключить обязательное исполнение неподдерживаемых инструкций.
   Первоначальный существующий RISC-V генератор нужен только для
   контрольного запуска компилятора. Он не заменяет генератор копирований.
4. Запустить препроцессирование и контрольную компиляцию GCC внутри

Нынешнее размещение допускает до 256 МиБ пространства и 64 МиБ гостевой
памяти RV32I. Достаточность для GCC ещё не измерена; выбирать размещение
по размеру настоящего ELF, статических объектов, стека и расходу кучи.
Подготовка загрузочного образа перелинковывает те же объекты cc1 с
гостевыми start/main/newlib операциями. Исходный ELF cc1 и его контрольная
сумма сохраняются; рецепт линковки берётся из сухого вызова его цели Make,
а не из выдуманного списка объектов. Начальный предел кучи — 16 МиБ,
памяти гостя — 64 МиБ, пространства — 256 МиБ; резерв стека минимум
4 МиБ проверяется по ELF. Исходники гостевой обёртки и команды фиксируются
рядом с образом. Создание образа само по себе не доказывает работу GCC.
Первый сквозной тест настоящего cc1 — препроцессирование C с вложенным
заголовком: исходники/argv упакованы в IN после образа, гостевой `-E -P`
выдаёт весь результат в OUT. Нативный GCC используется только как
контрольный эталон теста; исходник задания в рабочем пути разбирает cc1
в пространстве. Сохраняются полный журнал копирований, конечный дамп,
код завершения, весь OUT и контрольные суммы образа/задания.
Следующий контрольный режим компилирует тот же C через настоящий cc1
в RV32I-ассемблер, выданный в OUT. Только для проверки этот ассемблер
собирается подготовительными инструментами с коротким вызывающим кодом
и исполняется копированиями в отдельном пространстве. Проверяются полный
32-битный возврат 7, OUT `7\n` и код завершения 0. Это контроль генерации
cc1, а не готовый генератор прямых копирований или гостевая линковка.

Начальная часть генератора прямых копирований — модуль C
`runtime/gcc/copy_emit.c`. Он записывает поля копирований и числовые
константы в образ с указанной шириной адресов. 32-битное сложение
разворачивается в копирования с таблицей полного сумматора, без команд
RV32I, выборки или декодирования команд процессора. Операнды и результат
имеют существующее представление числовых полей LSB-first. Таблица,
временное поле и перенос размещаются отдельно от операндов, результата
и исполняемого слоя. Этот модуль пока не подключён к GCC; проверка
его образов не означает завершение этапа генератора GCC.

Новая цель GCC называется `copyspace-unknown-elf`. Начальная структура
RTL, ограничения операндов и соглашение вызовов берутся из небольшого
backend Moxie того же GCC 12.5.0; его машинные команды не исполняются.
Скрипт `scripts/gcc/prepare_target.py` создаёт отдельное дерево исходников
из ссылок на закреплённый GCC и изменённых файлов новой цели. Исходный
GCC не меняется. Все полученные файлы новой цели и исходные контрольные
суммы записываются в manifest.
Ассемблер копирований GCC содержит шаблоны `copy.*`, секции и символы;
их гостевое развёртывание в слои пока не реализовано. Регистры новой
цели означают числовые поля пространства, не регистры эмулируемого CPU.
ABI GCC копирований: little-endian, 32-битные int/long/указатели,
64-битные long long/double/long double, первые шесть слов аргументов
в полях r0..r5, остальные в стеке, возврат начиная с r0, SP и FP —
отдельные поля. Поля r6..r11 сохраняет вызываемая функция. Точные
смещения кадра задаются сохранёнными исходниками новой цели; перенос
байтовых адресов в битовые адреса выполняет будущая гостевая линковка.
Первоначальный backend отказывает при запросе big-endian и создании
трамплина вложенной функции: старые машинные трамплины Moxie не допускаются.
Это пока исходники цели, а не доказательство компиляции GNU C в копирования.
`build_cc1.py --copy-target DIR` принимает подготовленный каталог новой
цели, проверяет её manifest и фиксирует его суммы в профиле сборки.
Гостевые CC/CXX и библиотеки сохраняют RV32I/ILP32: это архитектура
исполнения GCC, а не результата. Для copyspace не передаются параметры
цели RISC-V `--with-arch/--with-abi`. `--configure-only` позволяет проверить
настройку перед большой сборкой; после него ELF cc1 ещё не подготовлен.

суммы проверенных исходников совпали с рабочими файлами. Доказательства:

Следующая часть `copy_emit` связывает несколько слоёв: отдельная область
кода хранит шаблоны, а слот 255 загружает очередной слой в активный слой 0.
При недостатке места генератор выделяет следующий слой до размещения
операции. Числовые поля и таблицы находятся вне всей области кода.
Первый слой образа загружает входной слой программы; остановка загружает
проверенную нулевую область. OUT обслуживается перед копированиями слоя,
поэтому для вывода вычисленного результата создаётся отдельный слой.
Такая связка не содержит выборки или декодирования команд RV32I.
Первая сборка новой цели остановилась в configure-build-libcpp: ссылка
на каталог libcpp перенаправляла `libcpp/../config.sub` в исходный GCC.
Поэтому библиотечные каталоги подготовки создаются отдельными реальными
каталогами с ссылками на их содержимое. Путь дерева входит в профиль;
предыдущая сборка и журнал сохраняются отдельно, повторная использует
новый каталог. Исходное дерево GCC по-прежнему не изменяется.
Связывание слоёв проверено прямым исполнением шести образов двух
последовательных сложений, включая перенос между битами и сброс переноса
перед второй операцией. Проверяются также нехватка места в области кода,
пересечение данных с кодом и отказ остановки через ненулевую область.
Сырые журналы: `tmp/gcc-copy-chain/*`. Гостевая проверка сохранённой
версии этой связки идёт отдельно в `space-tests/gcc-copy-emitter-chain`
на data/work; её успешное завершение пока не подтверждено.
Шаблоны вычитания и AND/OR/XOR разворачиваются тем же модулем C.
Вычитание использует таблицу разности и заёма с явным сбросом заёма
перед каждой операцией. Побитовые операции выбирают один бит из таблицы
двух аргументов; для них нужно 96 строк вместо 193 строк сумматора.
Это развёртывание при генерации образа, не дополнительные команды эмулятора.

только выходному тексту `<mul>.x`, имена RTL сохраняются. Заголовок
gencodes проверяется C++-компилятором, а не только кодом завершения
генератора. Если гостевые объекты gcc ещё не созданы, исправление MD
можно применить к текущему дереву и профилю, сохранив прежние MD,
manifest и профиль отдельно; нативные библиотеки не пересобираются с нуля.

Первое подключение ассемблера копирований выполняет гостевой модуль
`copy_link.c`: он разворачивает тело одной функции без вызовов, памяти
и переходов в прямой образ. Поддерживаются перемещения, константы,
add/sub/inc/dec и AND/OR/XOR. Начальные r0..r5 задаёт проверочный
вызывающий код; после возврата он выводит все 32 бита r0. Для разных
операций выделены разные неизменяемые таблицы: последующая генерация
XOR не должна менять таблицу предыдущего сложения. Неизвестная операция,
другая функция, секция данных или некорректный операнд вызывают отказ.
Это начальная часть будущей гостевой линковки; полноценные символы,
вызовы, память, перемещения и GNU linker scripts всё ещё необходимы.
Пять образов нативного модуля прошли прямое исполнение: смешанные
add/XOR, add/sub, OR/AND, перенос через ноль с inc/dec, octal-константа
и перемещение. Десять повреждённых или неподдерживаемых входов отвергнуты
без выдачи образа. Сырые журналы: `tmp/gcc-copy-link/*`. Тест
`tests/test_gcc_copy_link.py` повторяет проверки, сохраняет исходники
и запускает модуль в пространстве; его гостевой результат ещё ожидается.
Входы этого теста — самостоятельные фикстуры ассемблера, не выдача
настоящего GCC. Компиляция C новой целью и передача результата этому
модулю остаются отдельным обязательным этапом.
Сборка новой цели использует `default-common.cc`, как исходный Moxie:
`target_has_targetm_common=no`. Без этого GCC требовал отсутствующий
copyspace-common.cc. В печати смещений применяется
HOST_WIDE_INT_PRINT_DEC, потому что на гостевом RV32 HOST_WIDE_INT
имеет тип long long, а не long. Исправление сохраняет ABI и готовые
объекты, прежние manifest/профиль/исходники фиксируются отдельно.
Для меток гостевой линковки `cs_copy_program_patch_jump` записывает
статический переход между уже выделенными слоями. Проверяются границы
области кода и начало каждого слоя; произвольный адрес данных или
адрес внутри слоя не принимается. Это исправление поля источника
копирования в слоте 255, не команда перехода в эмуляторе.
Слой вывода результата выделяется отдельно от последнего блока тела:
ранний `copy.ret` не должен исполнять инструкции последней метки.
Проверка включает ранний возврат и недостижимый последний блок,
который меняет r0; прямой запуск должен сохранить значение возврата.

Следующие операции гостевой линковки — `copy.ashl`, `copy.lshr` и

нулевой бит. Проверяются количества 0, 1, 4, 31 и маскирование 32/63,

Унарные шаблоны `copy.neg` и `copy.not` имеют отдельный исходный регистр.
Отрицание разворачивается как вычитание из нуля, инверсия — XOR с
`0xffffffff`; используется существующий пул неизменяемых констант.
Проверяются различные исходный и конечный регистры и их совпадение,
включая 0, `0x80000000` и `0xffffffff`.
`copy.cmp` сохраняет результаты равенства, знакового и беззнакового
сравнения двух 32-битных регистров, не меняя сами регистры.
Таблицы истинности обрабатывают биты от младшего к старшему; старшее
различие заменяет результат младших. Знаковое сравнение учитывает
различие знаковых битов. Все десять `copy.branch.*` из MD используют

следующий блок. Таблицы адресов размещаются между нулевым слоем и

и начальные регистры аргументов. Они удаляются перед вызовом cc1;
после первого обычного аргумента GNU разбор частных аргументов прекращается.

в образ 64 КиБ, с адресной шириной профиля результата. Этот образ

Для длительного bootstrap добавляется отдельный режим наблюдения
`--trace-channels FILE`. Он записывает все реальные события IN/OUT,
число наблюдённых копирований и событий каналов (`counts C H`), затем
обычную причину остановки. Отдельные копирования в этом режиме не

только наблюдатель. Полный `--trace` сохраняет прежний формат.

он не заменяет полный журнал там, где нужно изучать отдельные копирования.

проверенного снимка (`fork_from`). Новая фаза сохраняет хеш исходной
конфигурации, сведения о предшествующих участках, хеш памяти и точные

частичная выдача незавершённой попытки не принимается. Старые журналы
и снимки сохраняются. Изменение входа или геометрии пространства
запрещено; новый бинарник наблюдателя и длина участка записываются явно.

## Настраиваемые пределы генератора

При сборке `copy_link.c` можно задать пределы меток,
переходов и вызовов через `CS_COPY_LABEL_CAPACITY`,
`CS_COPY_JUMP_CAPACITY`, `CS_COPY_CALL_CAPACITY`. Значения по умолчанию
32, 64 и 32 сохраняют прежнее размещение и выдаваемые образы.
Области переходов и адресов возврата расширяются вместе с
таблицами, начало кода перемещается вслед за ними. Псевдонимы и имена
отдельных входов используют предел меток. Остальные пределы пока
сохраняются; это не снимает ограничений для сборки Linux.
Проверка должна превысить каждый прежний предел и исполнить полученные
копирования с сырым журналом, а также проверить прежнюю выдачу побайтно.

Проверены четыре прямые программы при пределах 128/512/64: более
32 меток, 80 условных переходов, 40 вызовов и настоящая выдача GCC
для GNU C-программы из 40 функций (результат 43). GCC для последней
работал в диагностическом QEMU; генерация образа в этой проверке
выполнялась нативным C-генератором. Сырые журналы прямого исполнения
сохранены. Каждый прежний предел также проверен отдельно при
расширенных остальных таблицах. ASan/UBSan дали четыре одинаковых
образа; девять недопустимых конфигураций отвергнуты при сборке.

выходные байты, код завершения и stderr старого и нового генератора.

## Расширение символов и перемещений

Прежние пределы генератора — 12 разных адресных выражений в
инструкциях и 64 перемещения в начальных данных. Добавлены параметры
сборки `CS_COPY_SYMBOL_CAPACITY` и `CS_COPY_RELOCATION_CAPACITY`, по
умолчанию 12 и 64. Область адресных выражений в образе расширяется
вместе с таблицей, начало кода смещается; перемещения нужны только
при генерации. Подготовка cc1 передаёт оба параметра и сохраняет их
в манифесте. Проверка должна включать настоящую выдачу GCC для 80
глобальных переменных и для массива из 80 указателей, прямое исполнение
копирований и отказы при сохранённом прежнем пределе каждой таблицы.

Для выявления следующих препятствий дополнительно проверяется выдача
целевого GCC на сохранённых препроцессированных `lib/ctype.c`,
`lib/string.c`, `lib/sort.c`, `lib/rbtree.c` Linux 6.12 из аудита TCC.
Они подготовлены с заголовками RISC-V, поэтому такая диагностика
не является портом архитектуры Linux и не доказывает сборку ядра.

Проверка `tests/test_gcc_copy_symbols.py` завершилась: оба настоящих
GNU C-входа (компиляция в диагностическом QEMU) дали прямой результат
3240. Таблицы на 80 записей достаточны, 79 отвергается для каждой;
отдельно отвергнуты прежние пределы 12 и 64 при расширенных остальных
таблицах. ASan/UBSan дали побайтно одинаковые образы. Новый модуль
скомпилирован для RV32I; восемь дополнительных неверных конфигураций
подготовки отвергнуты. Прежние 46 программ прошли, 54 сохранённых
входа дали прежние байты образа, код завершения и stderr.
Гостевое исполнение этих двух новых больших входов ещё не проверено;
уже запущенные integrated-data/functions используют прежние замороженные
версии генератора.

Диагностика Linux 6.12: целевой GCC создал ассемблер для ctype
(1709 байтов), string (30722), sort (9588). Нативная проба линковки
с добавленной контрольной функцией остановилась соответственно:
строка 16 `assembly line too long`, строка 35 и строка 8
`operation outside leaf body`. В этих файлах директивы экспорта
содержат несколько операторов через `;`, включая `.previous`;
нынешний построчный разбор не исполняет их отдельно и оставляет
неверную активную секцию. Это следующий необходимый шаг разбора.
Компиляция rbtree остановилась на именах регистров RISC-V `tp` и `sp`
в arch/riscv/include/asm/current.h. Эти сохранённые препроцессированные
входы не заменяют собственную архитектуру Linux для копирований.

## Разбор операторов ассемблера

Разбор прямого и раздельного входа должен использовать общие границы
операторов: перевод строки, `;` и метка с `:` вне строковых литералов.
Комментарии `#` завершают физическую строку; символы внутри кавычек
и экранированные кавычки сохраняются. Номер ошибки относится к
физической строке, а не к количеству операторов. Вместо буфера 256
байтов выделяется буфер по самому длинному оператору входа; память
выделяет и освобождает гостевой C-runtime. Проверки должны покрыть
прямую и раздельную линковку, строки с `;`, `#`, `:` и экранированием,
экспорт Linux и фактическую длинную строку из ctype.c.
Дополнительная прямая проверка должна связать неизменённую выдачу GCC
для Linux sort.c с отдельно скомпилированной контрольной функцией,
отсортировать восемь чисел, проверить каждый элемент и вернуть 204.
Это диагностическая компиляция и нативная подготовка образа, а не
исполнение GCC внутри пространства или загрузка Linux.

Общий разбор реализован в прямой и раздельной линковке. По десяти
прямым случаям прошли ASan/UBSan, строки с кавычками/экранированием,
литералами `;#:` и строкой 20001 байт, комментарии и метки с командами
в одной строке. Таблица Linux ctype читается через адрес из её
`.export_symbol`, а не только по прямой ссылке. Отдельная обёртка
malloc/free проверила освобождение буферов при успехе и ошибках,
включая принудительный отказ выделения. Физический номер ошибки
сохранён. Прежние 46 программ и 47 случаев раздельной линковки
с 23 отказами прошли, включая точный размер временного буфера.

Неизменённая выдача целевого GCC для Linux sort.c связана с отдельной
контрольной единицей: сортировка массива `{8,3,6,1,7,2,5,4}`,
проверка каждого элемента на `i+1`, итог 204. Прямое исполнение вернуло
`cc000000`. ASan/UBSan сохранили образ побайтно; текущие исходники
также дали тот же образ, что и сохранённый сырой журнал исполнения.
Это настоящий код sort.c после диагностической компиляции GNU C,
но компилятор и линковщик этой проверки исполнялись вне пространства.
Гостевая проверка нового разбора ctype запущена отдельно в
`space-tests/gcc-copy-guest-ctype-statements-v2` на data/work, итог
пока ожидается. Её замороженная версия предшествует малой правке
поглощения перевода строки после метки в раздельном разборе.
Начальный каталог без `-v2` сохранён: запуск завершился отказом
старого бинарника эмулятора, не знающего `--trace-channels`.
В отдельную RV32I-фикстуру добавлена память для newlib `_sbrk`;
рабочая гостевая обёртка GCC использует собственный существующий heap.

Следующее препятствие выдачи Linux string.c — локальные цифровые
метки (`1:`, `1b`) и вставки RISC-V `ebreak` из BUG(), которые
требуют архитектурной реализации для копирований. Текущая проба
останавливается на строке 856 `invalid or duplicate copy label`.
